# ReachTether v1.1 Implementation Plan

This document turns the feature list in `Docs/v1.1.md` into a concrete implementation plan grounded in the current codebase.

## Current baseline

The existing robot runtime already has several strong seams we should preserve:

- A long-running host with DI and hosted services in `dotNet/ReachTether.Robot/Program.cs`.
- Two orchestrator modes:
  - `InteractionOrchestrator` for turn-based Responses API flow.
  - `RealtimeInteractionOrchestrator` for OpenAI realtime voice flow.
- Existing local tool execution for the camera:
  - Legacy path in `dotNet/ReachTether.Robot/InteractionOrchestrator.cs`
  - Realtime path in `dotNet/ReachTether.Robot/Realtime/Handlers/FunctionCallHandler.cs`
- Externalized personality definitions in `dotNet/ReachTether.Robot/personalities.json` and `dotNet/ReachTether.Robot/PersonalityCatalog.cs`.
- An already-registered but currently unused `ReachTether.Server` HTTP client in `dotNet/ReachTether.Robot/Program.cs`.

This means v1.1 should extend the current architecture, not replace it.

## Main architectural direction

v1.1 should split the system into two cooperating runtimes:

1. Robot runtime
   - Owns robot hardware access, low-latency audio, local camera capture, motion, and realtime session flow.
   - Stays small, predictable, and restartable.

2. ReachTether.Server + desktop UI
   - Hosts remote tools, knowledge, scheduling, sub-agents, persistence, and a desktop UI.
   - Acts as the durable system of record for sessions, artifacts, reminders, and long-running work.

The robot should remain the real-time edge process. The server should own stateful and slower-moving capabilities.

## Feature mapping from v1.1

### 1. Server offload and desktop UI

From `Docs/v1.1.md`:

- Remote Blazor app serving both backend APIs and desktop UI
- Robot video visible in desktop UI
- Camera tool snapshots visible in desktop UI
- Robot can call remote tools like Kinect capture and scheduler

Recommended direction:

- Implement `ReachTether.Server` as the application boundary for:
  - session persistence
  - tool execution
  - sub-agent orchestration
  - knowledge retrieval
  - artifact storage
  - UI state feeds
- Keep robot-side code focused on:
  - audio capture/playback
  - motion
  - local camera capture
  - OpenAI realtime transport
  - local fail-safe behavior when server is unavailable

### 2. Sub-agents and smarter models

From `Docs/v1.1.md`:

- Spawn sub-agents, track them, apply timeouts, collect outcomes
- Offload complex thinking to a smarter model

Recommended direction:

- Implement these as tools, not orchestrator-specific hardcoded branches.
- Make the default execution target the server, because:
  - timeouts and retries are easier to manage there
  - logs and outcomes can be persisted
  - heavier models do not burden the robot

### 3. Personality system

From `Docs/openclaw-personality-findings.md`:

- Personality should be layered rather than one large static prompt.

Recommended direction:

- Keep a short operational base prompt.
- Move identity and persona into durable files/config.
- Add situational overlays for session state, room mode, user relationship, and tool availability.

### 4. Knowledge and persistence

From `Docs/v1.1.md`:

- Store knowledge server-side and hydrate related knowledge on demand

Recommended direction:

- Robot remains a thin client for knowledge retrieval.
- Server owns:
  - vector search
  - full-text search
  - optional graph relationships
  - transcript summaries
  - user/session memory

### 5. Always-on behavior

From `Docs/openclaw-always-on-findings.md`:

- The effect comes from a persistent gateway, session reuse, heartbeats, queued events, and scheduled wakeups.

Recommended direction:

- Add always-on behavior at the server layer first.
- Keep the robot runtime responsive to server-pushed or server-polled events rather than trying to make the robot itself own all durable background state.

## The biggest current gap

The current runtime supports only a narrow version of tool use.

Today:

- Realtime session tool registration only adds `camera`.
- Realtime tool handling only knows how to execute `camera`.
- Legacy tool execution only meaningfully handles `camera`.
- System prompt augmentation is specific to the camera tool.

That is the first thing to generalize.

## Proposed v1.1 architecture

### A. Shared tool layer

Introduce a generic tool abstraction shared by both orchestrators.

Suggested interfaces:

- `IToolDefinitionSource`
- `IToolExecutor`
- `IToolRouter`
- `IToolExecutionContext`
- `IToolArtifactPublisher`

Suggested categories:

- Local tools
  - `camera`
  - local motion/gesture tools later
- Remote proxy tools
  - `scheduler`
  - `kinect_shot`
  - `knowledge_query`
  - `smarty_mode`
  - `spawn_subagent`

Responsibilities:

- Register the same tool schemas in both legacy and realtime modes.
- Route tool calls by name.
- Enforce timeouts.
- Return structured tool outputs.
- Publish tool artifacts to the server/UI when needed.

### B. ReachTether.Server client

Turn the existing `ReachTether.Server` HTTP client registration into a real typed client:

- `IReachTetherServerClient`

Suggested endpoints:

- `POST /api/tools/execute`
- `POST /api/subagents`
- `GET /api/subagents/{id}`
- `POST /api/knowledge/query`
- `POST /api/snapshots`
- `POST /api/session-events`
- `POST /api/heartbeat/run`

The robot should treat the server as optional but preferred. If unavailable, local capabilities should still work.

### C. Session model

Add durable session identity beyond the in-memory turn history used today.

Suggested concepts:

- `SessionId`
- `UserId`
- `ConversationLane`
- `TurnId`
- `ToolCallId`

The server should persist:

- transcripts
- tool calls
- tool outputs
- snapshot artifacts
- sub-agent jobs
- reminders and scheduled tasks
- heartbeat/system events

### D. Prompt building

Replace the current camera-specific `ToolPromptAugmenter` approach with a more general prompt builder.

Suggested layers:

1. Base operational prompt
2. Personality identity
3. Personality soul/style
4. Tool availability summary
5. Session overlays
6. Memory/knowledge overlays
7. Always-on/heartbeat overlays when applicable

This preserves the good part of the existing personality catalog while making it extensible.

## Per-feature implementation details

### 1. Remote Blazor app as backend server and desktop UI

Recommended design:

- One ASP.NET Core app that hosts:
  - API controllers
  - background services
  - Blazor UI
  - persistent storage integrations

The UI should show:

- current robot connection status
- current session/personality
- recent transcript
- current camera stream
- camera tool snapshots
- sub-agent jobs and statuses
- scheduled reminders/tasks

### 2. Streaming video from robot to desktop UI

Do not overload the camera tool path for live video.

Create a separate streaming path:

- `IRobotVideoPublisher` on the robot
- server-side stream receiver
- UI consumer in Blazor

Recommended first pass:

- publish sampled JPEG frames over WebSocket or gRPC stream
- display in desktop UI as a near-live feed

Why this first:

- it is much simpler than introducing full WebRTC end-to-end immediately
- it reuses current snapshot/camera knowledge
- it is enough for operator visibility and debugging

Possible future step:

- replace with proper media streaming if latency or bandwidth becomes a problem

### 3. Camera tool snapshots shown in desktop UI

The existing `CameraToolExecutionResult` already has most of the needed data:

- question
- snapshot bytes
- media type
- capture time

Extend the tool execution path so every camera tool call can optionally publish an artifact record:

- `artifactId`
- `sessionId`
- `turnId`
- `toolCallId`
- `source`
- `question`
- `capturedAt`
- tags

This should apply to:

- robot local camera snapshots
- remote server-side camera tools like Kinect capture

### 4. Remote tools: KinectShot, scheduler, server capabilities

Add a remote tool proxy mechanism.

Robot-side:

- register remote tool schemas as normal tools
- execute them through `IReachTetherServerClient`

Server-side:

- validate tool arguments
- execute tool with timeout/cancellation
- return structured result
- persist output and optional artifacts

Suggested initial remote tools:

- `scheduler`
  - create reminder or meeting task
- `kinect_shot`
  - capture image from server-attached camera
- `knowledge_query`
  - retrieve relevant memory/knowledge snippets
- `smarty_mode`
  - ask a slower/smarter model for help
- `spawn_subagent`
  - run a background agent workflow

### 5. Sub-agents and smarter models

Treat sub-agents as explicit jobs.

Suggested server-side model:

- `SubAgentJob`
  - `JobId`
  - `ParentSessionId`
  - `RequestedByTurnId`
  - `Status`
  - `StartedAt`
  - `DeadlineAt`
  - `ResultSummary`
  - `RawResultLocation`

Suggested execution behavior:

- Robot asks server to spawn sub-agent.
- Server immediately returns `jobId`.
- Server runs job with timeout.
- Completion becomes a session event.
- Robot sees the event on next sync/heartbeat or immediate push channel.

This maps well to the “system events later surface into the main session” model from the always-on findings.

### 6. Personality system v1

Current state:

- `personalities.json` stores a single instruction block per personality.
- runtime can hot-switch personalities by phrase.

Recommended v1.1 refinement:

- Keep `personalities.json` for compatibility, but expand the structure:
  - identity fields
  - soul/style fields
  - startup behavior
  - social overlays
  - optional allowed/disallowed tool tendencies

Suggested eventual structure:

- `identity`
  - display name
  - short self-description
  - voice style hints
- `soul`
  - tone
  - values
  - response preferences
- `startup`
  - arrival behavior
- `contextOverlays`
  - desktop UI mode
  - operator mode
  - always-on mode

Then create a `SystemPromptBuilder` that composes these pieces.

### 7. Knowledge and persistence

Current state:

- legacy conversation history is kept in memory only
- realtime session state is transient and tied to the OpenAI session

Recommended v1.1 direction:

- Server persists:
  - turn transcript
  - summaries
  - user facts
  - robot-discovered facts
  - tool outputs worth retaining
- Robot retrieves compact working context on demand rather than full history

Suggested retrieval modes:

- proactive hydration on session start
- on-demand `knowledge_query` tool
- automatic retrieval for selected intents

Start with:

- full-text + vector retrieval

Add later if justified:

- graph relationships

### 8. Always-on first pass

Do not attempt full “always alive robot consciousness” on the first pass.

Implement the transferable mechanisms from the OpenClaw findings:

1. Persistent session identity
2. Server-side heartbeat scheduler
3. Server-side event queue
4. Serialized work per session
5. Scheduled tasks/reminders
6. Silent no-op heartbeat behavior

Suggested flow:

- server heartbeat wakes every N minutes
- server checks pending reminders, completed jobs, important state changes
- if nothing matters, record no-op and do not interrupt user
- if something matters, enqueue a session event
- robot/UI consumes that event and can speak/show it when appropriate

## Risks and constraints

### 1. Tool explosion without a shared abstraction

If new tools are added directly into orchestrators, the code will become brittle quickly.

Mitigation:

- make the shared tool layer first

### 2. Tight coupling between UI and robot runtime

If the robot starts serving UI-specific data structures directly, the edge/runtime boundary will blur.

Mitigation:

- server owns UI-facing projections
- robot publishes domain events/artifacts, not page models

### 3. Realtime session complexity

The realtime session code is already subtle and timing-sensitive.

Mitigation:

- keep new behavior behind handlers/services
- avoid adding ad hoc branching directly into the turn loop

### 4. Always-on behavior becoming spammy

Proactive behavior can easily become noisy if heartbeats surface too much.

Mitigation:

- require relevance thresholds
- suppress no-op outputs
- route through a session event model first

### 5. Server availability

Remote tools and persistence introduce new failure modes.

Mitigation:

- keep local fallback behavior where possible
- mark tools as local-only, remote-only, or preferred-remote
- degrade gracefully when server is unreachable

## Recommended immediate next step

Start with Phase 1.

Specifically:

1. Introduce shared tool registration and execution interfaces.
2. Replace camera-specific tool wiring in both orchestrators with the shared tool router.
3. Add a typed `ReachTether.Server` client and config section, even if the first implementation is skeletal.

That gives us the base needed for nearly every other v1.1 item.
